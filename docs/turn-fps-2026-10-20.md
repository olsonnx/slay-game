# Sustained turn FPS — 20 October 2026

## Diagnosis

The reproduced large-map slowdown is primarily CPU-side. On the native RTX 2060 Forward+ / D3D12 run, GPU rendering typically took about 1.8–2.1 ms while slow simulation frames took 18–30 ms. CPU rendering itself took about 2 ms; scripting, authoritative command validation/commit, presentation updates, and snapshots consume additional time. A 60 FPS frame has a 16.7 ms budget, so a 10–18 ms command commit can consume most or all of it even when GPU work is inexpensive.

Measured GPU and CPU rendering time use Godot's viewport measurements. Those CPU measurements exclude scripts and other subsystems; see the [RenderingServer documentation](https://docs.godotengine.org/en/4.6/classes/class_renderingserver.html#class-renderingserver-method-viewport-get-measured-render-time-cpu). The delayed `Performance.TIME_PROCESS` monitor in early diagnostic captures was not used to classify individual frames and has been removed from the diagnostic summary.

The isolated Huge-map worker search completed in 853 ms, with a median frame interval of 4.926 ms and GPU time of 1.885 ms. Its 95th-percentile frame was 10.571 ms. The search is already on a worker thread; blindly moving more code to a thread is not the first fix. Live command commits must remain synchronized with the authoritative model and playback.

## Errors and fixes

The user's two repeating errors match the local game log: `remove_unit()` called `Array[Sprite3D].erase()` with a freed sprite. Typed arrays reject that value, so the stale reference remained and subsequent cleanups could print the same errors again. The posted stack is in map retirement, rather than worker AI search.

- Unit cleanup now removes entries by index, which safely removes freed references.
- Covered map retirement clears picking and idle registries once, avoiding repeated whole-army array scans while each tile is retired.
- Lighting caches sources by coordinate and checks only changed tiles during scoped notifications.
- Birds update stationary-unit tracking for affected coordinates. Initial loads and rewinds still rebuild complete tracking.
- Wildlife updates affected actors and tiles. Explicit actor death, clearing, and cancellation invalidate presentation so unchanged snapshots can still resynchronize it.
- Validating one movement command no longer generates every legal destination or evaluates every other border defender. It builds the friendly route graph and validates the chosen target; complete destination generation remains available for overlays and planning. Path equivalence is tested against that complete generator.

Full refreshes remain available for topology replacement and direct refresh calls. Scoped state exists only during synchronous board notification delivery. Graphics quality, game rules, and AI scoring are preserved.

## Remaining priorities

The next useful CPU targets are army batch scans/uploads, cheaper simulation snapshots, and capture/topology/replay bookkeeping. Their work still grows with army or map size. Reducing resolution would chiefly reduce GPU work; the measured GPU already has substantial headroom. The user's 8× MSAA adds GPU cost, but graphics quality should not be the first response to this measured CPU bottleneck.

## Follow-up: slowdown mainly with Ctrl

Ctrl uses 6× playback; it does not increase `Engine.time_scale`. The same commands, impacts and settlement work occur over a much shorter interval. Normal playback has many inexpensive animation frames between commits, while fast playback exposes the costly updates more frequently. The earlier measurements above already used Ctrl speed.

Two additional changes target that repeated work:

- Economy readout signatures check the notified coordinates against cached relevant records before scanning the whole map. Formerly relevant land, bridge support, treasury, inspected ownership, selection and turn context still invalidate the cache. Empty/full notifications always rebuild. The original complete signature remains the test oracle.
- A queued army refresh returns immediately if an explicit playback refresh has already consumed its pending request. Immediate source restoration for moving and dying sprites remains intact.

Native Huge / 1,019 tiles / 120 units, seed 71, same complete 122-decision round, uncapped Forward+:

| Ctrl 6× case | Mean FPS | 95th-percentile frame | Total board-listener CPU | Army refreshes |
|---|---:|---:|---:|---:|
| Before follow-up | 162.0 | 14.151 ms | 772.76 ms | 268 |
| After follow-up | 163.7 | 10.963 ms | 163.75 ms | 204 |

Typical board-listener cost fell from 4.448 to 0.210 ms. GPU median during animation stayed about 1.77 ms; animation draw calls remained about 734–735. Both rounds rebuilt 74 static chunks and performed 72 static synchronizations. Average FPS barely changed; expensive rule commits and snapshots remain. The maximum frame was worse in the follow-up capture (144.271 versus 113.782 ms), so this is evidence of reduced repeated notification cost and improved 95th-percentile timing, not elimination of all spikes. These are individual captures, not a statistical performance guarantee.
