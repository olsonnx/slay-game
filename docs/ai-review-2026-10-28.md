# Enemy AI performance review — 28 October 2026

The largest measured opportunity is avoiding repeated analysis during preparation. The project already has worker simulation, a strategic assignment planner, cached queries within a planning pass, validated movement batches, and incremental worker publication. Build on those systems.

This review adds diagnostic scripts and this document only. No gameplay behavior, version, executable, or ZIP was changed.

## Measurements from the current checkout

Godot 4.6.3, headless, Normal difficulty, seed 71, faction 1. These are synthetic developed boards from `tools/heavy_strain_probe.gd`: partitioned territory, tile value 6, 300 gold per bank, fixed randomly placed mixed-tier troops. They are not representative opening positions or recorded player saves. Runs are on this machine, without release-export optimization, and show noticeable timing variation. Three samples per case are enough for triage, not a performance guarantee.

First probe, inclusive wall time for one purchase-candidate pass and one complete strategic movement plan:

| Display size (internal ID) | Tiles | Total troops / faction troops | Purchase pass | Strategic plan | Legacy plan |
| --- | ---: | ---: | ---: | ---: | ---: |
| Tiny (`small`) | 86 | 30 / 1 | 18–44 ms | 15–22 ms | 50–96 ms |
| Standard (`large`) | 255 | 60 / 5 | 79–93 ms | 79–119 ms | Not measured |
| Huge (`huge`) | 1,019 | 120 / 11 | 525–599 ms | 340–474 ms | Not measured |

The Tiny comparison only involves one friendly unit; it does not establish that strategic AI is universally stronger or faster. Plans can differ, and these are single searches, not full movement phases.

A second probe measured actual `prepare_async` worker execution on a fresh Huge fixture for each sample. It made eight decisions and took **4,230 / 5,716 / 5,328 ms wall time** (chronological order in the raw file differs). Worker CPU elapsed times were 4,228 / 5,714 / 5,326 ms. No animations or renderer were involved. Synchronous full preparation in the same probe took 4,403–5,602 ms.

Isolated fresh `defense_needs` calls in that second probe took 235–461 ms. City-site checks took 0.5–3.8 ms, road proposals 18–28 ms, and bridge-target generation 0.8–5.2 ms for this faction. A subsequent purchase pass with already warmed queries still took 193–379 ms. These component calls are diagnostic, have different cache warmth, and must not be added as a precise exclusive breakdown. They show that threat analysis is substantial and that further purchase work remains after caching it. This fixture has few recruitment hubs; road planning may matter more in city-rich saves.

Full simulation snapshots in the first probe cost about 0.5–15 ms. They are not the leading cost on these strategic-board samples. The worker path already uses a cheaper borrowed analysis view and copies changed records between worker transactions.

Reproduce with the local Godot console, `--headless --path . --script artifacts/ai_review_probe.gd` or `artifacts/ai_review_stages.gd`. Use an absolute path with `--log-file` on Windows. ## Findings in the current implementation

1. **Preparation rebuilds analysis after every purchase.** `kingdom_ai.gd:120` runs up to 4/8/12 purchase passes for Easy/Normal/Hard. Each new planner creates new Queries. `ai_candidates.gd:12` generates options faction-wide and takes the best. `ai_queries.gd:499` scans enemy troops and builds their movement reach; `defense_needs` adds defense-sensitive projected capital threats. Existing caches only last one immutable planning position.
2. **Algorithm selection depends only on tile count.** `kingdom_rules.gd:68` selects legacy below 200 cells and strategic at or above 200. Legacy `ai_planner.gd:85` snapshots and evaluates the board for candidate branches, with extra reply work on Hard. Both planners can commit multiple compatible orders; legacy does not necessarily commit only one move. An army-heavy Small map can still be expensive despite its size.
3. **Reach finding uses a linearly scanned priority queue.** `logistics.gd:57` searches the pending array for the cheapest node and scans it again for membership. Edge costs are 1 or 2, with a small movement budget. `ai_logistics.gd` uses a similar queue for unbounded friendly travel costs. Numerous repeated searches amplify this overhead.
4. **The strategic limit applies after substantial work.** `ai_strategist.gd:99` enumerates and sorts options per source unit; `assign_unit` then checks up to 16/40/64 tactical candidates. The limit does not bound the preceding generation, scoring, frontier-distance loops, or full sort.
5. **Strategic memory lasts within a faction turn.** `opponent_turns.gd:102` creates a new controller each faction turn. Objectives survive replanning inside that turn but not across rounds. Persistent faction goals could improve coherence as well as reduce unnecessary reconsideration.
6. **Thinking and showing moves run in series.** `opponent_turns.gd:119` awaits animation before requesting the next movement batch. Worker threading keeps the UI responsive but leaves the player waiting for computation plus presentation.

## What the other games demonstrate

Civilization V's official update documents distinct economic, diplomatic, city, operational, tactical, and homeland AI responsibilities. Operations choose campaign targets and staging, while tactics handle units and combat positioning. This supports borrowing a hierarchy: faction goals → front objectives → unit assignments → local tactical checks. It does not establish exact thread counts, caches, or modern Civilization implementations. [Official Civ V update](https://store.steampowered.com/oldnews/5384).

EU4's developer describes separate defense and finance decisions, regional army assignments, coordinated offensives, and combat-strength estimates. One documented failure involved incompatible assumptions between fort budgeting systems. The lesson for our design is to share budgets and intent between planners, use good local estimates, and validate their interaction. Public descriptions do not expose its complete current scheduler or source. [Paradox's AI diary](https://steamcommunity.com/games/236850/announcements/detail/3123810455819551560).

The following changes are recommendations for this project, not claims that EU4 or Civ uses these exact algorithms.

## Recommended implementation order

### 1. Preserve decisions while eliminating repeated work

- Introduce a preparation analysis context with separately versioned topology, occupancy, economy, and defense data. Reuse enemy route/reach results while their dependencies remain unchanged; refresh local defense, projected capital threats, wages, affordability, and recruitment opportunities after a buy. Keep a full-recompute fallback for bridge changes, spells, ownership changes, or uncertain dependencies. Do not simply retain the existing Queries object: its contract requires an immutable position.
- Build indexes of armies, hubs, and frontier cells once per relevant revision. Before exact enemy pathfinding, use a conservative distance bound to reject enemies that cannot reach any relevant frontier even on the cheapest legal road. Preserve bridge and road cases. This is an exact rejection, not arbitrary range culling.
- Reuse purchase-independent facts and defer work for impossible categories. For example, avoid building bridge proposals when affordability already rules them out; keep city-saving policy and urgent defense intact.
- Replace linear Dijkstra queues with stable integer buckets or a tested heap. Match the existing reachable set, costs, parent paths, and deterministic equal-cost ordering. Topology adjacency can be cached independently of changing ownership.
- Instrument searches once per invocation, rather than summing per-order decision annotations that can share the same planner. Record preparation, reach, candidate generation, tactical scoring, rules commit, worker handoff, and playback separately.

These changes should aim for identical actions and replay outcomes. Their benefit must be measured; the current data does not justify promising a fixed multiplier.

### 2. Spend thinking where it affects the outcome

- Trial strategic assignment on Tiny/Small as well, keeping legacy available for comparison. Replace the tile-only switch with a measured workload policy, or use one strategic backend plus selective tactical search.
- Precompute frontier-distance fields and shared objective values. Maintain a bounded best-candidate set instead of fully sorting every option. Preserve the same candidate order where claiming equivalence; early heuristic pruning can change decisions and needs strength testing.
- Reserve deeper local lookahead for capital defense, supply cuts, knight trades, bridge control, and close tactical contests. Routine uncontested movement needs much less work. Keep emergency defensive options even if their initial heuristic score is low.
- Retain per-faction campaign objectives across rounds, but revalidate against the new board. Store intent separately from command sequences; discard obsolete plans on elimination, load, restart, or rule change. Add a switching threshold so nearly tied goals do not oscillate. Include persistent state in save/replay reconstruction if it affects deterministic decisions.
- Use deterministic work limits for decisions; wall-clock deadlines alone can make outcomes depend on the machine. Hard should invest additional tactical work in critical situations rather than repeat all global bookkeeping more often.

### 3. Reduce visible waiting

Plan the next batch on a private worker state while already committed moves animate. Hold publication until playback reaches the appropriate boundary. Keep cancellation, pause, replay order, and presentation snapshots correct; invalidate on encounters or state changes. This overlaps work rather than reducing CPU cost. Do not compute different factions' authoritative turns concurrently from the same stale board.

If profiling still identifies route or scoring kernels as dominant after these steps, consider native code for those small kernels. A full rewrite or more worker threads is premature.

## Acceptance criteria

- Capture ordinary early/mid/late player positions alongside synthetic Huge and city-rich boards; cover all difficulties.
- For exact optimizations, compare legal options, costs, stable ties, chosen commands, final state, RNG behavior, and replay playback against baseline.
- For policy changes, use paired seeds with faction positions rotated, compare outcomes, capital survival, starvation, supply defense, and obvious missed tactics. Win rate alone can hide a recurring tactical mistake.
- Report median and slow-tail full faction/round CPU time, time to first visible action, worker handoff spikes, and playback time. Retain pause/cancel/restart and event invalidation checks.
- Start with preparation reuse and route finding, then reassess. The measurements already establish multi-second preparation without animation; they do not yet establish the cost distribution of a complete played round.
